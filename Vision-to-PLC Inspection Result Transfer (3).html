1. Problem Identification & System Boundary

A camera on a robotic arm inspects parts moving on a conveyor. Image processing runs on a high-performance PC; the arm controller and the pneumatic reject actuators are driven by a local PLC.

RoleSystemResponsibility
SourceVision PCAnalyses each part (variable processing time) and produces the inspection result.
Target (interface)PLC-side interface or gatewayValidates the request, de-duplicates by part_id, stores the result in the part-tracking queue, acknowledges.
Target (control)PLCTracks parts, sequences arm motion, commands the pneumatics, enforces interlocks and safety, reads the stored result at the decision point.
Why manual transfer or direct wiring is insufficient. The result must reach the PLC bound to the correct moving part and before that part reaches its decision point. Manual transfer (screen reading, HMI entry, files, USB) is too slow and error-prone. Direct digital I/O stays right for simple signals such as the camera trigger, but a few wired bits cannot carry part identity, confidence, acknowledgement or a log. The API complements hardwired signals.
System boundary. The API transfers inspection data only. It does not trigger the camera, command arm motion or valves, or perform safety functions, and an acknowledgement never proves a physical sorting action occurred. The PLC alone decides how to act.

2. API Design & Specification

POST/api/v1/inspection-results

The path names a resource (plural noun) and carries the API version so the contract can evolve. POST fits because each call creates a new inspection-result resource; duplicate safety comes from the unique part_id. REST/JSON is chosen for simplicity; OPC UA could carry the same contract.

{
  "part_id": "P-000123",
  "result": "REJECT",
  "confidence": 0.94
}

part_id: unique identifier issued by the PLC tracking at the camera trigger (1 to 32 characters of A-Z a-z 0-9 _ -). result: ACCEPT or REJECT. confidence: JSON number between 0 and 1. All fields are required; unknown fields and wrong types are rejected.

CodeMeaning
201 CreatedResult received and stored: {"part_id":"P-000123","status":"STORED","received_at":"…"}
200 OKIdentical repeat: original acknowledgement returned, nothing stored again.
409 ConflictRESULT_CONFLICT (same part, different result), DEADLINE_EXPIRED, or PART_NOT_TRACKED.
422 / 5xxInvalid payload, rejected / interface fault.

STORED confirms reception and storage only, not that the PLC has acted.

Validation rules [REQ]

FieldTypeRule
part_idstringRequired, 1 to 32 characters of A-Z a-z 0-9 _ -
resultstringRequired, ACCEPT or REJECT

3. Execution Model & Latency Justification

Synchronous submission
The vision PC waits for the acknowledgement: it needs proof, within bounded time, that the PLC side holds the result, so it can retry or alert.
Asynchronous action
The PLC reads the queue and acts when the part reaches the decision point. The robot never waits on an HTTP call.
Near Real-Time
Safety stays in the PLC and safety hardware; the useful window is seconds; standard Ethernet and HTTP suffice. No safety certification is claimed.

With distance L and conveyor speed v: Tavailable = L / v, and the budget must satisfy Ttotal ≤ Tavailable.

Value0.60 m, 0.25 m/s2.40 s0.900.100.100.300.401.80 s0.60 s

Reserve R = 2.40 − 1.80 = 0.60 s. The latest usable instant is td = 2.40 − (0.10 + 0.30 + 0.40) = 1.60 s.

Latency, timeout and retry are distinct. [TGT] API latency P95 ≤ 100 ms (4.2 % of Tavailable). [ASM] Per-attempt timeout 250 ms. [REQ] A retry may start at time t only if t + timeout ≤ td, with the same part_id.

Worst case: attempt 1 starts at 0.90 s and times out at 1.15 s; the retry ends by 1.40 s ≤ 1.60 s. A third attempt would end at 1.65 s > 1.60 s, so one retry only.
SituationHandling
Incorrect part_idMalformed: 422. Not in the tracking queue: 409 PART_NOT_TRACKED, logged, nothing actuated.
Duplicate messageIdentical: 200, one queue entry. Different result: 409 RESULT_CONFLICT, original kept.
Timeout or missing resultPart marked unconfirmed; at td the PLC applies a configurable fail-safe route and logs NO_RESULT.
Late result409 DEADLINE_EXPIRED: logged, never applied.

Worst-case retry timeline (seconds)

Each attempt may start only if it can finish by td. The third attempt cannot, so the PLC fail-safe applies.

4. Value Proposition

Integration
A versioned JSON exchange decouples the vision algorithm from PLC programming.
Traceability
Each result is tied to a part_id, a reception time and an acknowledgement.
Reliability
Validation, duplicate handling, deadlines and explicit codes prevent silent errors and double decisions.

Validation test (optional Part 3)

The request from the brief was sent to httpbin.org, a public service that echoes back what it receives, to check that the request and its JSON formatting are correct.

ItemValue used
ToolMini Postman (mobile app), Manual Input mode
Method and URLPOST https://httpbin.org/post
Content typeapplication/json
Body{"part_id":"P-000123","result":"REJECT","confidence":0.99}

What the response shows

Request received as sent
The echoed method is POST and the Content-Type header is application/json.
JSON correctly parsed
The json field returns part_id, result and confidence as a structured object, so the payload is well formed.
Limits of this test. httpbin only echoes a well-formed request. It does not enforce the validation rules of section 2 or return 201, 409 or 422, and it is not the interface described in this brief. No server implementing this API was built or tested, so this test checks the request format, not the API behaviour.
